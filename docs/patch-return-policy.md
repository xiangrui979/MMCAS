# 队友机本地补丁回传约定（v1.2）

> 背景：实战中出现过队友在**已安装包**（`pkg/` 内）上直接热改代码（如面板 v2），
> 改动有效但**未回流开发仓**，回收时需靠 diff 反推。本约定把这类改动制度化。

## 允许的热改场景

热改**只允许**发生在赛季进行中、且**等待开发仓修复会阻塞比赛**时。改动对象限：

- `pkg/plugins/dsh-panel-mmcas/lib/*`（面板）
- `pkg/core/**/*.mjs`（核心脚本）

禁止热改：`setup.bat`、`start-*.bat`（装机链路）、任何 `secrets/`（凭据）。

## 回传要求（热改人必做）

1. **改前留底**：把原文件复制为同名 `.bak-<日期>`（如 `index.js.bak-0914`），与改动文件同目录。
2. **记录 memory**：在 `workspace/memory/<角色>/` 写一条记录：改了什么文件、为什么、如何验证（命令与结果）。
3. **写卡标注**：在相关任务卡或新建一张卡（owner=modeler，标题前缀 `[热改回传]`），写明文件清单与验证方式。
4. **不 commit 到工作区仓**：`pkg/` 不属于工作区仓（工作区仓只含 `workspace/`、`tasks/`、`memory/`、`notices/`）。

## Modeler 侧回收流程

1. 赛季结束后（或收到 `[热改回传]` 卡后），通过 SSH 从队友机拉取变更文件（或要求队友把 `.bak-*` 与改动文件打包发回）。
2. 在开发仓逐条 diff 审查 → 合入对应源文件（`packages/...`）→ 跑回归测试（`test-poller` / `test-taskcard` / `test-notice` / `test-audit`）。
3. 合入后在原卡批注"已回收 + commit 哈希"，并更新 `docs/design.md`（如涉及行为变化）。
4. 下一次打包随包下发——**队友不需要手动回滚热改**（新包覆盖）。

## 为什么这样设计

- 热改是**战时行为**，赛后必须收敛回仓，否则下一轮打包会用旧代码覆盖，形成"修了又丢"的循环。
- `.bak-*` + memory + 卡三件套保证**任何改动可追溯、可审查、可复现**，同时不阻塞比赛期的机动性。
- 回收由 Modeler（唯一有 SSH 与开发仓的角色）执行，责任单一。
